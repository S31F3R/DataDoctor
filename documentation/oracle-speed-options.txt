Oracle / HDB over the network — speed options (discussion only; not implemented)
================================================================================
Context: Internal HDB uses many short SQL round-trips (per SDID × date chunk ×
thread). Wall time is usually dominated by network RTT + Oracle parse/execute,
not by local Python after the PATH bug fix.

Current shape (USBR.sqlRead)
----------------------------
- Estimate points for the full date range → split into date sub-ranges (chunks)
  when over queryLimit rows.
- For each (SDID, chunk): open connection, run interval SQL, optionally r_base
  SQL, close connection.
- Up to maxThreads (15) workers pull those tasks.
- Map/lookup tables (agency, method, …) use one connection first.

Why a 2-year × many SDIDs query is slow
---------------------------------------
- Tasks ≈ (# HDB series) × (# date chunks). Chunks grow with range/interval.
- Each task pays connect + 1–2 SQL round-trips over the internet (or WAN).
- Two HDB homes (LCHDB + YAOHDB) are separate query groups; still same Instant
  Client process, but each sqlRead has its own worker pool and task list.

Options to speed up (pick later; tradeoffs)
------------------------------------------

A) Batch SDIDs in one SQL (WHERE site_datatype_id IN (...))
   - One round-trip for many series in the same chunk/DB.
   - Biggest win for “100 parameters” style lists.
   - Need careful bind limits (Oracle IN list / array binds), result split by SDID,
     and memory for large multi-series result sets.

B) Fewer / smarter date chunks
   - Larger queryLimit or adaptive chunking → fewer tasks, fewer connects.
   - Risk: bigger result sets, longer single statements, more chance of timeout.

C) Connection reuse / pool per thread (or per sqlRead)
   - Worker opens one connection and reuses it for many tasks instead of
     connect/close per (SDID, chunk).
   - Cuts login/handshake cost a lot over the internet.
   - Must be thread-safe (one connection per thread only).

D) Connection pool (oracledb pool) shared carefully
   - Acquire/release instead of full client setup each time.
   - Helps multi-query sessions; still need A or B for true multi-series speed.

E) Database links / single DSN strategy
   - Already uses primary DSN + @db_link for secondary HDBs.
   - Ensure all HDB work rides one authenticated session tree where possible.

F) Parallelism tuning
   - maxThreads vs DB/session limits vs network congestion.
   - More threads can help or hurt (session storms, lock/contention).

G) Reduce metadata work when not needed
   - Skip r_base merge / map lookups for public or “values only” mode if product allows.

Recommended order of attack (when you green-light efficiency work)
------------------------------------------------------------------
1. C — per-worker connection reuse (low risk, big cut on connect spam)
2. A — multi-SDID IN-list queries per chunk (biggest win for wide queries)
3. B — tune chunk size for long ranges
4. D/F — pool + thread count after measuring

Not recommended as first step
-----------------------------
- More threads alone without A/C (more connects, more PATH/session stress).
- Client-side “fake” monthly/yearly for USGS (API has no such collections).
