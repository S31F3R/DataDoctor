Oracle / HDB over the network — speed options
================================================================================
Context: Internal HDB uses many short SQL round-trips (per SDID × date chunk ×
thread). Wall time is dominated by network RTT + Oracle parse/execute.

Current production path (bug-smashing)
--------------------------------------
- Option C: each worker opens ONE Oracle session, runs many (SDID, date-chunk)
  tasks, then closes. executeCustomQueryWithRetry reconnects once if the session
  drops.
- Date chunking still uses queryLimit for large ranges.
- maxThreads still 15 (not increased).

Seifer validation
-----------------
- Day query: HDB ~60s slower than USGS/Aquarius after C — good improvement.
- 2-year mega query: HDB only ~30s slower than Aquarius after C — good enough.
- Option A (IN-list multi-SDID) made things slower → REVERTED to C-only.

Options history
---------------

A) Batch SDIDs IN-list  — TRIED, REVERTED (slower than C alone)

B) Fewer date chunks  — REMOVED (too risky)

C) Connection reuse per worker  — SHIPPED / keep
   CODE: USBR.sqlRead worker() owns one oracleConnection for its task queue.

D) Connection pool  — DEFERRED (C covers the win we care about)

E) DB links  — already in place where available

F) More threads  — leave alone unless profiling says otherwise

G) Skip metadata  — REMOVED (needed for details)

Bottom line
-----------
Stop here for Oracle speed unless a new bottleneck appears. Prefer not to re-try
A without a measured plan (bind batch size, fetch cost, DB plan).
